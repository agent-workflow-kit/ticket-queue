# ticket-queue: interface

Status: 0.1.0-design. Written before implementation (architecture §18.1). This document is the single normative source for ticket-queue's rules; `docs/design.md`, the README and the architecture link to its headings and never restate its tables. The `--json` shapes, hook payloads, config, log records and the re-rank documents are specified in [schemas/](../schemas/).

ticket-queue answers "which ticket should I do next?". It keeps a local pool of candidate tickets per board, read through ticketctl, decides which are eligible, scores them deterministically, optionally lets a model re-rank the top of the list, applies the user's pins and skips, and hands out the top ticket, optionally reserving it with a claim. It never writes to the ticket system: a claim is a local reservation, and status, assignee and sprint changes belong to the caller (through ticketctl).

## Concepts

### Identifiers

A ticket is identified by `(site, key)`. A key matches `^[A-Z][A-Z0-9_]*-[0-9]+$`, is accepted in any letter case and is printed upper-case. A ticket argument is `KEY` or `<site>:KEY`, where `<site>` is a ticketctl site name (`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`); a browse URL is not accepted (a caller passes the key). `--json` output always carries `key` and `site`.

The site of a ticket argument is resolved in this order: `site:KEY`; else `--site`; else the one site whose store holds the key (several: exit 21 `ambiguous_key` with the candidates in `details.candidates`); for a key in no store that needs a live read: `ticketctl.default_site`, else the only site any board names; else exit 2 `invalid_argument`, reason `site_required`. For `release`, `unpin` and `unskip` the third step is narrower: the site is the one whose store has a claim (`release`), a pin (`unpin`) or a skip (`unskip`) for the key; several exit 21 `ambiguous_key`; none exits 0 with `unchanged: true` and `site` null.

When a read returns a canonical key that differs from the stored one (a moved ticket), the store merges in the same transaction. With no row for the canonical key, the row is re-keyed. Otherwise a live claim on the canonical key wins and the other claim ends (`post-release`, reason `merged`), else the claim moves; the earlier pin position and the later pin expiry are kept (null is latest); one skip remains (untimed beats timed, `auto` beats `human`, else the later `until`); `consecutive_failures` takes the maximum; member rows are united. The old key is kept as an alias that resolves on input and is never a ticket row. An alias is recorded only when a `get` returned `requested_key`. Aliases are one hop: a merge repoints every alias that named the merged-away key to the canonical key. A key returned as a ticket by any read is real: an alias with that name is deleted in the same transaction (a real key beats an alias, also when a key is reused). Input resolves an alias with one lookup. A moved ticket stored twice (a search returned the new key before any `get` recorded the alias) stays two rows until the next complete full rebuild removes the old row's member rows and `prune` deletes it. `prune` deletes aliases whose target row is gone. `requested_keys` is the ticket's aliases, sorted (`[]` when none, at most 20, the newest). It is carried, and required, by every object that identifies a ticket with `key` and `site`: the ticket object, the `claim`, `pin` and `skip` objects, `claims` entries, `passed_over` entries, the top level of `release`, `pin`, `unpin`, `move`, `skip` and `unskip` outputs, every ticket hook payload and `changed_claims` entry, and ticket log records. Board hooks carry `[]`. `browse-result.json` (ids only) and error envelopes do not carry it. Every writer canonicalizes through one store function in its own transaction.

Other identifier grammars: a board name matches `^[a-z][a-z0-9_-]{0,63}$`; a label key matches `^[a-z0-9][a-z0-9_.-]{0,63}$` and a label value is 0 to 256 characters from `[A-Za-z0-9._:/#@+=,-]` (architecture §8.1; a label is split at the first `=`); a holder is 1 to 256 characters from the label-value set (`--holder ''` exits 2); an actor matches `^(human|auto):[A-Za-z0-9._@-]{1,64}$`; a decision id matches `^[A-Za-z0-9._:@/-]{1,128}$`; a duration matches `^[0-9]{1,6}(ms|s|m|h|d|w)$` in flags and config. Every identifier is matched with `fullmatch`. An identifier that fails its grammar exits 2 `invalid_argument`.

### Boards, pools and candidates

A **board** is a named entry in config. It names a ticketctl **site** and a **source** (a ticketctl named query, or structured flags), plus the board's goals, prioritized epics, parent allow and deny lists, eligibility rule settings, signal weights and re-rank settings. A **pool** is the set of tickets fetched for a board and stored. A **candidate** is a stored ticket that is eligible.

A ticket is in a board's pool when that board's last fetch returned it (a membership row records `first_seen` and `last_seen`). Its owner is the first enabled board, in current config order, whose pool holds it; ownership is computed when read, and that board's goals, weights, epics and rules apply to it. Member rows of an excluded or removed board are ignored when read (their deletion at the next `refresh` or `prune` stays). A ticket in no pool is not a candidate; it stays stored while it has a claim, a pin or a live skip, and otherwise until `prune` (`retention.tickets` after `last_seen`), so `why` can still explain it. A ticket in no pool has no board, score or position; `show`, `why` and `claim` evaluate it with the built-in default rules.

A board with `enabled: false` is **excluded**: it is never refreshed or selected, owns no ticket, and never affects an exit code or `post-refresh`; `boards` lists it with status `excluded` and `validate` checks its config. `--board B` naming an excluded board exits 10 `not_found` with a message saying it is excluded.

### Eligibility rules

Eligibility is decided locally on the stored ticket, not by the ticket system. Each ticket has a verdict per rule, `pass`, `fail` or `unknown`, and a rule that is `unknown` excludes the ticket just as `fail` does. The reason string of an exclusion is the rule name, or the rule's unknown reason. Rules are **soft** (a pin overrides them) or **hard** (nothing overrides them).

| Rule | Kind | Passes when | Unknown reason |
|---|---|---|---|
| `done` | hard | the stored `status.category` is not `done` | none |
| `gone` | hard | `gone_at` is not set (a `get` reporting the ticket not found sets it; a later read that returns the ticket clears it) | none |
| `hidden` | hard | the row is not a tombstone, and neither the project matches `hidden.projects` nor any label matches `hidden.labels` (globs `*` and `?`, fullmatch, ASCII case-insensitive; the matcher is described below) | none |
| `claimed` | hard | no live claim exists | none |
| `skipped` | hard | no active skip exists | none |
| `status` | soft | `status.category` is in `rules.status_category` | none |
| `pointed` | soft | `estimate` is not null and `incomplete` does not contain `estimate` | `estimate_unknown` (when `incomplete` names `estimate`) |
| `sprint` | soft | per `rules.sprint`: `open` passes when a sprint with state `active` is in `sprints`; `open_or_future` also passes a `future` sprint; `any` always passes | `sprint_unknown` (when `sprints` is null because the field was not read) |
| `unblocked` | soft | `blocked.value` is false | `blocked_unknown` (when `blocked.value` is null) |
| `assignee` | soft | per `rules.assignee`: `me_or_none` passes an unassigned ticket or one assigned to the site's account; `me`; `none`; `any` | `assignee_unknown` (when `incomplete` names `assignee`), `me_unknown` (the comparison needs the site's account and none is stored) |
| `parent` | soft | the ticket's `epic.key` and `parent.key` are in none of the board's `parent_deny` keys, and, when `parent_allow` is not empty, at least one of them is in `parent_allow` | none |

"The site's account" is the `account_id` stored from `ticketctl whoami` for the ticket's site; a null `account_id` on either side never matches. With no stored account (`whoami` failed), the comparisons that need it are unknown with reason `me_unknown`, and a `reassigned` claim state is not reported.

A rule with its setting turned off (`false` or `any`) always passes. `claimed` and `skipped` are decided from the store, not from the ticket, at the `now` of the command. A pin overrides every soft rule and never a hard rule (see [Manual order](#manual-order)). `eligible` is true when every rule passes (for a pinned ticket: every hard rule passes).

A hidden ticket is never printed by `list`, `show`, `why`, `next` or the TUI and never reaches a re-rank. The project of a ticket is its key's prefix. The store writer evaluates `hidden` on every read with the current config; a hidden read replaces the stored row with a tombstone (`site`, `key`, `labels`, `read_at`, `hidden_at`, no other field), still writes its member row and blanks the stored `reason` of the ticket's skip. A hidden read never deletes a pin or a skip (the hard rule `hidden` already blocks the ticket), and a claim stays. A tombstone keeps `read_at`, and the writer compares it like any row's. With `hidden.labels` not empty, a read whose `incomplete` names `labels` keeps the stored labels and evaluates `hidden` on them (no tombstone, no deletion); only a first read with no stored row is stored as a tombstone (fail closed). A later read that is not hidden stores the full row again. The rule `hidden` fails for a tombstone and for a stored row that the current config hides. The glob matcher is iterative (the matcher family of `LIKE`, never a regular expression), works on the label cut to 256 characters, folds case for ASCII letters only and treats `[` as a literal character; a list has at most 100 patterns. `claims` lists a hidden claimed ticket with `hidden: true` and its key only. `claim`, `pin`, `move`, `skip`, `show` and `why` of a hidden key exit 20 `refused`, reason `hidden` (a renewal included). `prune` deletes tombstones that are not claimed, pinned or under a live skip, with their member rows.

### Store

The pool, membership, claims, pins, skips, re-rank results and the hook outbox live in ticket-queue's private state database. Its only readers are ticket-queue's own commands. `list`, `show`, `why`, `claims`, `next` without `--claim` and `browse` read the store and never contact ticketctl.

Verdicts, signals, scores and the order are computed when read, from the stored ticket, the claims, pins, skips, membership and account tables, the current config and one `now` taken at the start of the command. Every read command reads the store inside one read transaction, so its output is one snapshot. A claim, pin or skip past its end is not live from that instant, whether or not a writer has removed it yet. A board's `refreshed_at` is the commit time of its last complete or truncated fetch, null before the first. `stale` is true for a board whose `refreshed_at` is null or older than `refresh.stale_after`; the top-level `stale` is true when any selected board is stale. `list`, `show`, `why`, `next`, `claims` and `boards` carry `refreshed_at` (a map of board to that time or null) and `stale`; state-changing outputs do not. The files and records are specified in [Files](#files).

**Housekeeping sweep.** Every command that changes local state (`refresh`, `claim`, `next --claim`, `release`, `pin`, `unpin`, `move`, `skip`, `unskip`, `rerank`, `prune`) first runs one sweep inside its own transaction: it ends lapsed claims (`release` record, reason `lapsed`, `post-release`); drops pins that expired or whose ticket is `done` or `gone` (`pin_dropped`, reason `expired`, `done` or `gone`); deletes skips past `until` (no record); and, only when the stored hash of the normalized `hidden.*` lists (kept on the `boards` data or a meta row) differs from the current one, replaces every stored row that the current config hides with a tombstone and deletes the `rerank_results` rows that name a tombstoned key, then stores the new hash. A pin of a ticket in no enabled board's pool is dormant and is not touched by the sweep (see [Manual order](#manual-order)). With `--dry-run` it reports and writes nothing. Read commands apply the same tests without writing: an expired pin is not pinned, and a done or gone one is `pinned_blocked`.

## Commands

Global flags where meaningful: `--json`, `--config PATH`, `--site NAME`, `--verbose`, `--quiet`, `--yes`, `--actor <actor>`, `--decision-id <id>` (repeatable, accepted and logged), `--dry-run` (every command that changes local state), `--version`. `--site NAME` on `list`, `next`, `refresh` and `boards` selects the boards on that site, on `claims` the claims whose `site` is NAME, and on a ticket argument it resolves the site. `--quiet` suppresses stdout on success and every non-error stderr line; for `refresh`, a board failure is printed to stderr only when it fires `post-refresh` (a status or error-code change, or the `hooks.refresh_repeat` reminder), and the exit code is unchanged. `--yes` is accepted and ignored (no command asks for confirmation; the dashboard passes it, architecture §7.6). Every command that outputs data supports `--json`; errors go to stderr and, with `--json`, to stdout as `{"error": {"code": "...", "message": "...", "reason": null, "details": {...}}}`. `error.code` is a closed class per exit code and `error.reason` is a separate field, null when not used (see [Exit codes](#exit-codes)). Text that can carry ticket or agent text (`--reason-file`) is taken as a file or `-`.

The default actor is `human:<me.name>` when stdin is a TTY, else `auto:unknown` (design guide §6). `--actor` is advisory. Records and payloads the tool causes itself (a lapse, a `prune` or `dead_grace` release, a `merged` release, `pin_dropped`, `hook_failed`, refresh and re-rank records) carry actor `auto:ticket-queue` and `actor_source: system`, whatever command ran them. Every log record carries `actor_source`: `flag` (`--actor` was given), `default`, `tui` (a TUI action) or `system`; the records of `release`, `skip`, `unskip`, `pin`, `unpin` and `move` also carry `tty`. `--force` requires `/dev/tty` to open and stderr to be a TTY, else exit 2 `invalid_argument`, reason `human_only`.

| Command | Purpose |
|---|---|
| `refresh [--board B] [--full] [--rerank]` | Read each board's pool through ticketctl and update the store |
| `list [--board B] [--all] [--skipped] [--claimed] [--query Q\|--query-file F] [--default-query] [--limit N]` | Print candidates in order |
| `show KEY` | Print one stored ticket with its verdicts and state |
| `why KEY` | Explain a ticket's score, verdicts and position |
| `next [--board B] [--claim] [--holder H] [--ttl D] [--label k=v]... [--query Q\|--query-file F] [--default-query] [--refresh]` | Print the top eligible ticket, optionally claiming it |
| `claim KEY [--holder H] [--ttl D] [--label k=v]... [--renew]` | Reserve a ticket, or renew a claim |
| `release KEY [--failed] [--holder H] [--force]` | End a claim |
| `claims [--holder H] [--label k=v]... [--board B]` | List live claims with their ticket state |
| `pin KEY [--top] [--expires D]` | Append a ticket to the pin list |
| `unpin KEY` | Remove a pin |
| `move KEY (--to N\|--top\|--before KEY\|--after KEY)` | Reorder within the pin list, pinning first when needed |
| `skip KEY [--for D\|--until T] [--reason-file F]` | Remove a ticket from candidates |
| `unskip KEY` | End a skip |
| `rerank [--board B] [--dry-run]` | Run the model re-rank |
| `boards` | List the configured boards and their state |
| `validate [--probe]` | Check config, plugin, ticketctl and claude-session; `--probe` also makes one real re-rank call |
| `cron install\|uninstall [--interval D]` | Manage the crontab block |
| `export [--since T] [--after-seq N]` | Print `log.jsonl` records |
| `prune [--dry-run]` | Remove old records |
| `browse [--focus KEY] [--board B] [--interval D] [--result-file PATH]` | Terminal UI |

`--board` takes one board; an unknown board exits 10, and so does a board with `enabled: false` (the message says it is excluded). `--board B` on `list`, `next` and `claims`, and the TUI's board tab, select the tickets B owns; `list --board B` shows the pinned tickets B owns in global pin order. `--version` prints `ticket-queue <semver>`. Every command that changes local state (`refresh`, `claim`, `release`, `pin`, `unpin`, `move`, `skip`, `unskip`, `rerank`, `prune`, `next --claim`) supports `--dry-run`, which reports what it would change and writes nothing; `claim --dry-run` and `next --claim --dry-run` do the live reads, evaluate in memory, store nothing and print the ticket they would claim. `unpin`, `unskip` and `release` are idempotent; `next --claim` is not: each call claims at most one ticket, and a retry after a lost result can claim a second, so after an unknown outcome a caller runs `claims --holder H`. No command takes an external action, so no command is confirm-by-default and none exits 13 in 0.x.

A command that needs a ticket treats a key by this table. `show` and `why` never read live.

| Command | A key not in the store |
|---|---|
| `claim`, `skip` | read live with `ticketctl get` and stored (in no pool); not found exits 10 `not_found`; a hidden key exits 20 `refused`, reason `hidden` |
| `pin`, `move` | exit 20 `refused`, reason `not_in_pool` |
| `release`, `unpin`, `unskip` | exit 0 with `unchanged: true` |
| `show`, `why` | exit 10 `not_found` with `details.boards` (each board's name, site and source) and a message saying the ticket is in no pool |

### refresh

`refresh` is the only command that reads pools from ticketctl. It processes the selected boards (all enabled boards by default, each in its own lease, see [Concurrency](#concurrency)); a board whose lease is held by another process is skipped and the command exits 0 and says "already running" for it. Each board stores a `source_hash` (sha256 of its site, its normalized source and the normalized `hidden.projects` and `hidden.labels` lists). On a mismatch the next refresh of the board is a full rebuild and deletes the board's stored re-rank result. A change of `hidden.*` therefore makes the next refresh of every board a full rebuild, which restores tickets no longer hidden. A ticketctl named query's text is not visible to ticket-queue: after editing it, run `refresh --full`. A board that is removed, renamed or excluded loses its member rows at the next `refresh` or `prune`; its claimed tickets stay (owner none) and its pins become dormant (see [Manual order](#manual-order)).

Once per site per refresh run it first reads the account: `ticketctl whoami --site S --json` (`--refresh` with `refresh --full`); the account (`account_id`, `display_name`) is stored per site. A failed `whoami` does not fail the board: the run uses the stored account, and with none stored the board reports the warning `me_unknown` in its `warnings[]` (in `refresh` and `boards`).

A board's refresh has two phases. The **fetch phase** makes every ticketctl call (step 1, then the reads of step 3) and holds the results in memory; step 3's re-read set is computed from the stored rows overlaid with the fetched tickets, ownership computed with the fetched member rows. The **commit phase** applies steps 2, 3 and 4 in one `BEGIN IMMEDIATE` transaction and makes no call. A failed fetch (step 1) skips the commit phase; a failed re-read never does (its keys count in `counts.departures_unchecked`). With `--dry-run` the fetch phase runs and nothing is committed.

For each board it then does, in order:

1. **Fetch.** A named-query source runs `ticketctl search --query <name>`; a structured source runs `ticketctl search` with `--project` (`projects`), `--type` (`types`), `--label` (`labels`), `--assignee` (`assignee`, each of `none` and `me`), `--sprint` (`sprint`, each of `open` and `future`) and `--status-category new --status-category indeterminate` (a done ticket is never a candidate, so it is not fetched). Every search passes `--site`, `--limit 500`, `--fields key,title,type,status,assignee,reporter,priority,estimate,sprints,parent,epic,labels,due_date,created,updated,blocked,url,incomplete` (the `description` is not requested: a rich-text page could fail the whole board) and pages with `--cursor`, at most `refresh.max_pages` calls (default 20). An **incremental** refresh passes `--order-by updated:asc` and `--updated-since <watermark minus refresh.overlap>`; a **full** rebuild (`--full`, the first refresh of a board, a `source_hash` mismatch, or the board's `last_full_at` older than `refresh.full_every`) does not. The fetch holds every page in memory. A fetch is **complete** when ticketctl returned `next: null`, **truncated** after `refresh.max_pages` calls without it, and **failed** on any error. A failed fetch commits nothing: rows, member rows, the watermark and `last_full_at` are unchanged. The ticketctl output is read through a 64 MiB cap; more is `lower_failed`, reason `output_too_large`. Every ticketctl child (in any command) runs in its own process group and is killed after 300 seconds of wall-clock time (ticketctl's own `--timeout`, default 120 s, bounds its provider work; this is the backstop); a kill is `lower_failed`, reason `deadline`.
2. **Upsert** each returned ticket by `(site, key)` through the store writer (a hidden read becomes a tombstone, a moved key is canonicalized), store its normalized fields, and upsert this board's member row (`first_seen`, `last_seen`). Every ticket row stores `read_at`, the time its read was issued (for a search page, the time that page's call started). The store writer ignores a read older than the stored `read_at` for that ticket, including its effect on `gone_at`; a stored `read_at` later than the writer's `now` (a local clock stepped back) counts as `now`, so a read at `now` wins; the member row of a fetch is still written. This covers search, departure `get`, claim `get` and TUI `r`. A field named in the ticket's `incomplete` keeps its stored value. The stored `incomplete` is the last applied read's list; a rule or signal is unknown when the stored `incomplete` names its field, even when the kept value is not null. A stub (a ticket ticketctl could not parse) changes nothing but `incomplete` and sets `degraded: true`, which `show` prints. A search upsert never clears the stored `description`.
3. **Re-read.** `ticketctl get` (grouped by site, batches of 50, the fields of step 1 plus `description`) for: every claimed or pinned ticket the board owns; on the first selected board of each site in config order, also every claimed ticket of that site that no enabled board owns; and the 100 tickets the board owns that pass every rule, first by deterministic score with the tie-breaks of [Ordering](#ordering). A re-read updates a ticket's fields (status, assignee, sprints, links, deletion) and never adds or removes a member row. Its results are applied in the commit phase. Each key is mapped on its own: a ticket updates the row (stores `description`, cut to 8 KiB, and `description_read_at`) and clears `gone_at`; `not_found` sets `gone_at`; any other per-key error (`forbidden` included) leaves the row unchanged and is counted in `counts.departures_unchecked`. An exit 10 or 12 with `details.errors` is read per key the same way; any other failure marks the whole batch unchecked. A ticket whose status category becomes `done` is stored as such (`state_since` records when a ticket became done or gone, for `claim.dead_grace`). A ticket outside the re-read set is updated when it changes (`updated`) or at the next full rebuild. A ticket that stopped matching the board's source (a label, component or filter change) stays a member, and one that started matching without `updated` changing stays absent, until the next complete full rebuild.
4. **Remove.** After a complete full rebuild (not truncated, not failed), delete this board's member rows for tickets it did not return. Tickets are not deleted here; a ticket with no member row, no claim, no pin and no live skip is removed by `prune`.
5. **Re-rank** when `--rerank` is given, or when `rerank.auto` is true and the rules of [Re-rank triggers](#re-rank-triggers) allow it. A failed or skipped re-rank never fails the refresh; its per-board results are the `rerank` member of the output.

The **watermark** is the time taken before the board's first call, after a complete fetch; after a truncated incremental fetch it is the largest `updated` returned. The overlap also absorbs up to 5 minutes of clock difference with the ticket system. A truncated full rebuild commits its upserts, skips step 4 and leaves `last_full_at` and the watermark unchanged, so the next refresh is a full rebuild again; a board larger than `max_pages × 500` tickets is truncated on every run, so narrow its source.

A ticketctl failure of one board commits nothing for that board and marks it with the status and error below; the other boards still refresh.

| ticketctl code or reason | Board status | `error.code` | Rows | Retry |
|---|---|---|---|---|
| ticketctl not found on `PATH` | none (no board is processed) | `tool_missing`, exit 12 error envelope naming the install command | kept | once installed |
| `rate_limited` | `refresh_failed` | `lower_failed` | kept | the board is not called until `retry_after` and stays `refresh_failed` |
| `cursor_expired`, `cursor_invalid` | `refresh_failed` | `lower_failed` | kept | restart without a cursor once, then fail |
| reasons `invalid_query`, `invalid_value`, `unknown_site`, `unknown_field`, any `invalid_config`; code `ambiguous_site` | `disabled` | `invalid_argument`, reason `invalid_config` | kept | next refresh; the board stays `disabled` until a refresh succeeds |
| `auth_required`, `bad_credentials` | `refresh_failed` | `lower_failed` | kept | the message names `details.token_env` |
| `forbidden`, `unavailable`, `timeout`, `provider_changed`, `partial`, any other | `refresh_failed` | `lower_failed` | kept | next refresh |

`lower_error` is `{exit, code, reason}` copied from ticketctl (with `tool`). A board's `retry_after` (in `boards[]` and `post-refresh`) is the seconds remaining at output time, null when none is pending. A board whose tickets all have `incomplete` naming `estimate` reports the warning `estimate_ambiguous` in its `warnings[]` with the ticketctl config key to set (`fields.estimate`). A board's `boards[]` entry in the output of `refresh` carries `already_running`, `mode` (`incremental` or `full`), `fetch` (`complete`, `truncated` or `failed`) and `counts` `{fetched, upserted, members_removed, departures_checked, departures_unchecked}`; its `warnings[]` carries `departures_unchecked` when that count is above 0. The top-level `mode` is `full` or `incremental` when every board that ran used that mode, `mixed` otherwise, and null when no board ran.

`post-refresh` fires on changes (see [Hooks](#hooks)). The exit code of `refresh` is in the rules table of [Exit codes](#exit-codes).

### list, show, why

`list` prints candidates for the selected boards in the order of [Ordering](#ordering), after the query filter, and always exits 0 (`empty` is true when nothing matched). The default set is the candidates; `--all` is every ticket of the selected pools (eligible first in Ordering, then ineligible by deterministic score with the Ordering tie-breaks, `position` null), with their exclusion reasons; `--skipped` and `--claimed` select those sets (both together are their union; with `--all` the flag is redundant) and, without `--all`, use the `--all` order (eligible first in Ordering, then by deterministic score with the Ordering tie-breaks, `position` null). `--limit` is 1 to 1000 (default 50), else exit 2; `total` counts after the query and before the limit. `--query` applies [Query language](#query-language) with `ORDER BY` allowed; with no `ORDER BY` the order is `ORDER BY position`. `--query` with `--query-file` exits 2 `invalid_argument`. The configured `browse.query` is applied only with `--default-query` (on `list` and `next`); `--default-query` with `--query` or `--query-file` applies both, joined with `AND`. An invalid `browse.query` under `--default-query` adds the top-level warning `browse_query_invalid` and is not applied; for `next`, an `ORDER BY` in `browse.query` is dropped with the same warning and the filter applies.

`show KEY` prints the stored ticket (the fields of the `ticket` object of the schemas, plus `description` and `description_read_at`, and `degraded` for a stub), its verdicts, state (`pinned`, `claimed`, `skipped`) and `refreshed_at`; `show` is the only command that prints the description. `why KEY` prints, for a ticket: the board, each signal's raw value, normalized value, weight and contribution (terms to two decimals for display), the total, the verdict of each rule with the exclusion reason, the pin, move and skip state with warnings for soft rules a pin overrides, the consecutive failures and `last_failure_at`, the re-rank result (position, reason, age, whether it applied), the claim state, and the position with the effective score. All text from the ticket is sanitized (control, format and invisible characters become `<U+XXXX>` markers). Both read the store only.

### next

`next` prints the top eligible ticket of the selected boards in the order of [Ordering](#ordering). It takes `--query`/`--query-file` for filters only; a query containing `ORDER BY` exits 2 (`invalid_argument`, `reason: order_by_not_allowed`), so the ranking stays the contract of `next`. `--holder`, `--ttl` and `--label` without `--claim` exit 2 `invalid_argument`, reason `claim_required`. With `--refresh` it first refreshes the selected boards that are stale, with the re-rank step off, and proceeds on the committed rows (the exit code of a partial refresh is in the rules table of [Exit codes](#exit-codes)). With no eligible candidate it exits 22 (see [Exit codes](#exit-codes)).

With `--claim` it takes the claim by the steps of [Claims](#claims). The candidate list is the order of [Ordering](#ordering) at the start of the command and is fixed for the command. Candidates are read in that order, in batches of up to 10 consecutive candidates of one site per `get`; every candidate examined counts toward `claim.scan_limit` (default 20). Each read candidate is re-evaluated on the fresh ticket with all rules; one that fails is listed in `passed_over` (`{key, site, requested_keys, outcome: claim_skipped, reason}`, `reason` the failing rule's name, `gone` for not found, or `read_failed` for any other per-key error); the first that passes is claimed in one transaction and printed. The reads are stored (not with `--dry-run`) and never change the list order. `next --claim` never returns a ticket with a live claim. A refresh older than `refresh.stale_after` does not block a claim. When none passes within the limit the command exits 22 with `passed_over` listed and, when the limit was reached, the warning `scan_limit_reached`. A `get` failure (ticketctl unavailable) exits 12 with `details.lower_error` and claims nothing.

### Ordering

The order of candidates is: first the **pin list** (in pin order) restricted to pinned tickets that an enabled board owns (a dormant pin is skipped) and that pass the hard rules; then every other eligible ticket by **effective score** descending, then `created` ascending (older first, null last), then site, then key by project (ASCII) and number (numeric). `position` is the 1-based position in this order for the selected set (all boards by default); it is null for an ineligible ticket and for a ticket in no pool. A pinned ticket that fails a hard rule is `pinned_blocked`: it is ineligible, listed with `--all` and by `why`, never counted in `total`, and never handed out; `boards` counts them. The **effective score** is the deterministic [score](#scoring), except for tickets covered by an applied re-rank result (see [Re-rank](#re-rank)).

### Scoring

The score of a ticket is the sum over signals of `weight × signal`, each signal normalized to 0..1, using its owner board's weights. Terms are exact rationals (Python `fractions.Fraction`); a config number is converted with `Fraction(str(value))`. Terms are summed exactly and the total is rounded once, half up, to two decimals; ordering compares the rounded totals. In `--json`, `normalized` and `contribution` are rounded half up to 4 decimals and the total to 2; text output shows terms to two decimals. A signal whose input is unknown contributes 0 and is shown as `unknown`; an absent optional value that is known absent (no due date) is 0 and shown as `none`. The order across boards follows the weights (raising a board's weights raises the board); `validate` warns `weights_differ` when the boards' weight sums differ. Defaults and formulas:

| Signal | Input | Normalization | Unknown when / none when | Default weight |
|---|---|---|---|---|
| `priority` | `priority.name` | `signals.priority_map` (entries overlay the defaults per name, case-insensitive; defaults Highest 1, High 0.75, Medium 0.5, Low 0.25, Lowest 0); a name not in the map falls back to `max(0, 1 - priority.rank / (signals.priority_levels - 1))` (`priority_levels` default 5) | null field: none (0); a name not in the map with `rank` null: unknown | 40 |
| `sprint` | `sprints[].state` | an `active` sprint 1, only a `future` sprint 0.3, none 0 (`signals.sprint.active`, `.future`) | `[]`: none; null: unknown | 25 |
| `epic` | the higher of the values for `epic.key` and `parent.key`, against the board's `prioritized_epics` (n entries) | the key at index `i` (from 0) gives `1 - i/n`; not listed 0 | never unknown | 20 |
| `due` | `due_date` | `d` is the due date minus today's UTC date, in whole days (negative when overdue): `d <= 3` gives 1, `d >= 30` gives 0, else `(30 - d) / 27` | no date: none | 20 |
| `assignee` | `assignee` | assigned to the site's account 1, unassigned or another person 0 | unknown when `incomplete` names `assignee` or the account is unknown | 10 |
| `age` | `created` | `min(days / 90, 1)`, days being today's UTC date minus `created`'s UTC date | `created` null: unknown | 5 |
| `labels` | `labels` | `min(sum of signals.label_bonus[label], 1)` | never unknown | 0 |
| `size` | `estimate` | `max(0, 1 - estimate / 13)` | `estimate` null: unknown | 0 |

The weights and signal settings are per board and overridable (see [Config](#config) for the bounds). `why` prints every term.

### Re-rank

Re-rank is optional (`rerank.enabled`, default false) and advisory: a failure, an expired result or no result leaves the deterministic order. It reorders only the tickets it was given.

**Candidates given.** The top `rerank.top_n` (default 20, at most 30) tickets the board owns, by deterministic score, that pass every rule and are not pinned. A board's re-rank covers only its own tickets; with no such ticket the run is skipped with reason `no_candidates`.

**Applying a result.** A stored, valid, unexpired result is applied in five steps:

1. Covered tickets are the result's keys that the board still owns, that pass every rule and are not pinned.
2. The slots are the current deterministic scores of the covered tickets, highest first.
3. The covered tickets, in result order (`ranking`, then `excluded` in deterministic order; an excluded ticket's result index continues after the last `ranking` index), take the slots in order.
4. The sort key is (effective score descending, result index ascending with uncovered tickets last, `created` ascending, site, key).
5. A dropped ticket's slot disappears; a new ticket keeps its deterministic score.

`rerank.position` is the 1-based index in `ranking`; an excluded ticket has `position` null and `excluded: true`; `ranking` may be empty. A result is applied only until `rerank.ttl` (default 24 hours) after it was made, and is shown as `rerank: expired` after that. `list --json` and `why` report whether a result applied, its age, and each ticket's re-rank position and reason. A re-rank never changes eligibility, the deterministic score or the pins.

Example: A has score 50 and was created in June, B has 50 and was created in May, C has 40; the model returns A, B, C. The slots are 50, 50, 40, so A takes 50, B takes 50 and C takes 40. The result index is a sort key after the effective score, so A (index 0) sorts before B (index 1) although B is older, and the order is A, B, C.

#### Re-rank triggers

`rerank [--board B]` runs a re-rank for the selected boards now. With the global `rerank.enabled` false the command exits 20 `refused`, reason `rerank_disabled`. With it true, a board whose own `rerank.enabled` is false is skipped with `rerank_disabled` in the output unless `--board` names it. `refresh --rerank` runs it after the refresh; with the global `rerank.enabled` false it refreshes and reports the re-rank step skipped with `rerank_disabled` (the exit code is not affected), and `refresh --rerank --board B` runs a board whose own `rerank.enabled` is false, as `rerank --board B` does. Manual runs (`rerank`, `refresh --rerank`) are never blocked by `min_interval`, `daily_limit` or the backoff, and count toward them. With `rerank.auto: true` every refresh runs it, but only when the **input hash** differs from the last valid, unexpired result's. The hash is the sha256 of the canonical JSON of the candidate keys sorted lexicographically (the key set), the goals text, the prioritized epics, the skill, the model, `top_n`, `description_chars`, and the plugin directory hash (sorted relative paths plus bytes) or the `rerank.command` argv; ticket text and scores are excluded on purpose (cost). The hash is computed on the candidate set before any drop; validation step 6 compares against the keys actually given (after drops). An expired result never blocks a run.

Every started run counts toward `rerank.min_interval` (default 1 hour) and `rerank.daily_limit` (default 8 per local day, the machine's local day). After a failed automatic run the next automatic attempt waits `min_interval`, doubling up to 24 hours, reset by a success. A blocked automatic run is logged as `rerank_skipped` with the reason (`unchanged`, `min_interval`, `daily_limit`, `rerank_disabled`, `no_candidates`, `backoff`). `post-rerank` fires only for failed runs, and a failed run logs `rerank` with `outcome: failed`. `--dry-run` prints the input document that would be given to the command and calls nothing. `next` and `list` never run a re-rank.

#### Slot contract

The re-rank slot is run by a command. `rerank.command` is an argv list run without a shell, or null (the default), meaning ticket-queue's bundled implementation (below). A custom command receives the **input document** on stdin and prints the **output document** on stdout; exit 0 means the output is to be used, any other exit is a failure. Ticket text never travels in argv or environment. The command runs in a private empty directory with a built environment (`PATH`, `HOME`, `LC_ALL=C` and the names in `rerank.env_allowlist`), under `rerank.timeout`, in its own process group which ticket-queue kills on expiry (group signals are allowed only for groups ticket-queue created, and a group is signalled only before its leader is reaped). Its stdout is read up to 32 KiB plus one byte (more: `output_invalid`), its stderr up to 4 KiB and shown sanitized, and stdin is written while stdout is read; its timeout is `deadline`. The command should exit on stdin EOF; a SIGKILL of ticket-queue does not stop it. `validate --probe` runs it on the sample (`sandbox_active` null).

The **input document** (schema `schemas/rerank-input.json`) is a JSON object: `schema_version` (1), `run_id` (32 random hex characters), `board`, `goals` (the board's trusted free text, at most 2000 characters, or an empty string), `prioritized_epics` (keys in order) and `candidates` (the top tickets in deterministic order: `key`, `position` (the 1-based index among the given candidates), `deterministic_score`, `signals` (the normalized values), and the ticket fields `title`, `description`, `type`, `status`, `priority`, `estimate`, `sprint`, `epic`, `parent`, `labels`, `due_date`, `age_days`). The mapping is: `type` is `type.name`, `status` is `status.name`, `priority` is `priority.name` or null, `sprint` is `active` when an active sprint exists, else `future`, else `closed`, else `none`, `age_days` is null when `created` is null, and `description` is null when no `get` has stored one. Every untrusted field is cut before the size is measured: `title` 200 characters, at most 20 labels of 64 characters, `epic.title` and `parent.title` 120, `description` `rerank.description_chars` (default 1000, maximum 1000). The ticket text fields (`title`, `description`, `labels`, the titles of `epic` and `parent`) are untrusted (`x-untrusted`).

The **output document** (schema `schemas/rerank-output.json`) is a JSON object with exactly the keys `schema_version` (1), `run_id` (echoed), `ranking` (best first: objects `{key, reason}`; it may be empty), `excluded` (optional, objects `{key, reason}`) and `skill_marker` under the marker rule below. `reason` is at most 200 characters and untrusted. The document is at most 32 KiB.

**Validation.** ticket-queue checks the output in this order, and any violation discards the whole result, keeps the deterministic order, logs `rerank` with `outcome: failed` and a reason from the table below, and fires `post-rerank`:

1. Read at most 32 KiB plus one byte; larger is `output_invalid`.
2. Decode strict UTF-8.
3. Check the nesting depth iteratively, at most 64, before parsing; brackets inside strings and escaped quotes are skipped.
4. Parse as a JSON object, rejecting duplicate keys at every level, `NaN`, `Infinity` and overflowing numbers. Every exception raised while decoding or parsing (an integer over Python's digit limit, a recursion error, a decode error) is `output_invalid`.
5. Require the exact key set above; `schema_version` is an integer and not a boolean; `run_id` matches the run. Every `ranking` and `excluded` entry is an object with exactly the keys `key` and `reason`, both strings.
6. Match keys by `fullmatch` and compare `ranking` plus `excluded` to the keys actually given (after drops) exactly (no invented, duplicate or missing key).
7. Sanitize every `reason` at ingest (a lone surrogate becomes a marker) and cut it to 200 characters after sanitizing. The schema's `maxLength: 200` is the author's contract; ticket-queue cuts a longer reason instead of rejecting it.
8. Check `skill_marker` by the marker rule below.

A re-rank failure is never a failure of the command that triggered it (`rerank` itself exits 12 with `rerank_failed`, see [Exit codes](#exit-codes)).

| Reason | Meaning |
|---|---|
| `tool_missing` | claude-session is not installed |
| `tool_too_old` | claude-session is older than 0.37.0 |
| `sandbox_unavailable` | `rerank.sandbox` is `required` and the sandbox cannot start |
| `launch_failed` | claude-session refused the launch (exit 12), or a name in `required_env_names` is not present; claude's own version problems arrive here |
| `unreported` | the run ended without a report (claude-session exit 14) |
| `blocked` | the run reported `blocked` or `needs-input` (exit 13) |
| `timeout` | claude-session reported its own timeout or turn limit (exit 16) |
| `session_failed` | any other non-zero claude-session outcome |
| `artifact_missing`, `artifact_invalid` | no artifact, or it failed parsing or its size check |
| `run_id_mismatch`, `marker_mismatch` | the echoed run id is wrong, or `skill_marker` breaks the marker rule |
| `keys_mismatch` | the key sets do not equal |
| `command_failed`, `output_invalid` | a custom command exited non-zero or printed an invalid document (or more than the output cap) |
| `input_invalid` | the input document exceeded its limits (a guard; the per-field caps make it unreachable by content) |
| `deadline` | ticket-queue's own guard expired (the `exec` guard, or a custom command's timeout) |

**Bundled implementation.** It uses claude-session directly (binding A, kind `rank`, headless, no agent-spawn). ticket-queue requires claude-session 0.37.0 or later and checks `claude-session --version` before the first run (`tool_too_old` otherwise). claude-session is called with `PATH`, `HOME`, the XDG variables, `LC_ALL=C` and the names in `claude_session.pass_env` (default `[]`; list `ANTHROPIC_API_KEY` there when Claude Code has no stored login), never with ticketctl's names. Before `exec`, every name in `start`'s `required_env_names` must be present, else the run fails `launch_failed` naming it and is stopped and forgotten. `validate` warns `pass_env_overlap` when a name is in both `pass_env` lists. Durations are passed to claude-session as whole seconds.

The sequence is: write the input to a private run directory (mode 0700, files created exclusively and never following links); `claude-session start --kind rank --mode headless --skill <rerank.skill> --prompt-file <prompt> --input-file <candidates.md> --plugin-dir <plugin directory> --permission-profile <profile file> --sandbox <rerank.sandbox> --setting-sources "" --env-allowlist-only <names>... --model <rerank.model> --timeout <rerank.timeout> --max-turns <rerank.max_turns> --label owner=ticket-queue --label rerank=<run_id> --label rerank_until=<unix seconds> --actor auto:ticket-queue --json`; then `claude-session exec --session-id <id> --run <n> --outcome-file <private path> --json`, where `<n>` is `run` from `start --json`, guarded at `rerank.timeout` plus 10 seconds (on expiry: `stop <id> --grace 2s`, then SIGTERM to the exact `exec` child, then SIGKILL after 2 seconds); then `claude-session status <id> --json` to read `run.report.artifact` (`path`, `sha256`, `size`), `run.sandbox_active` and the session's `csession_dir`. The artifact path from `status --json` must lie under `<state root>/private/<csession_id>/runs/<n>/artifact/` (the state root is `dirname(dirname(csession_dir))`) and must not lie under `csession_dir`; it is opened once without following links (a regular file, one link, owned by the user, at most 32 KiB), the sha256 and size computed from that descriptor's bytes are compared with the reported `sha256` and `size` and must equal them, and the document is parsed from the same bytes. The validated result is copied into ticket-queue's store, then `claude-session forget <id>` runs and the run directory is deleted. It passes no `--repo` (boards span repositories). The outcome is usable only when the exit code is 0, the outcome is `done`, `report.implicit` is false and the artifact is valid; anything else is a failure. On any failed step it lists `claude-session list --label rerank=<run_id> --json`, stops every non-final session and forgets it; a failed `forget` or `stop` is left to `claude-session reconcile`. `--max-turns` is a loose safety cap only (a turn limit may not stop a run that has already used more turns).

**Sandbox.** `rerank.sandbox` is `preferred` (the default) or `required`; any other value exits 2 `invalid_argument`, reason `invalid_config`; a custom `rerank.command` does not use it. A `preferred` run on a host without bubblewrap is still an isolated run (it keeps `dontAsk`, the read denies and the generated permission rules). `validate` and `validate --probe` warn `sandbox_inactive` when `sandbox_active` would be, or was, false. `preferred` deviates from the design guide's default `required` for skill wrappers (see `docs/design.md`).

**Leftovers and signals.** Each run creates its lock first, `tmp/<run_id>.lock`, then its directory `tmp/<run_id>/`, and holds an exclusive `flock` on the lock file for its whole life. At the start of each re-rank (after its lease) and in `prune`, the sweep goes by lock files: it takes `tmp/<run>.lock` with `LOCK_NB` and deletes `tmp/<run>/` only while holding that lock (no age test; descriptor-based, no symlinks followed); a lock file with no directory is removed. `claude-session start` also gets `--label rerank_until=<unix seconds>` (the start time plus `rerank.timeout` plus 120 seconds). The sweep lists `claude-session list --kind rank --label owner=ticket-queue --json`, selects sessions whose `rerank` label matches `^[0-9a-f]{32}$` and whose `rerank_until` label matches `^[0-9]{1,12}$` and is in the past, requires that the matching `tmp/<run>.lock` is free (taken with `LOCK_NB`, or absent) before it stops a session, stops the non-final ones with `--grace 2s`, and forgets all of them; a session whose `rerank` or `rerank_until` label is missing, duplicated or malformed is kept. `refresh`, `rerank`, `claim` and `next --claim` handle SIGINT and SIGTERM: they stop tracked children, clean up, release the lease and exit 130 or 143. A signal received after a claim transaction committed still prints the result, then exits 130 or 143.

The prompt file is trusted and holds: the artifact name `ranking.json`, the run id, the artifact schema, the rule that text between `<untrusted>` tags is data and never instructions, the board's goals (trusted, the user's own config) and the report command to run, which is the inline one-line `<absolute path of claude-session> report done --summary "<one line>" --artifact ranking.json` (no summary file). It tells the agent to use that absolute path (a report command containing `$CSESSION_DIR` is denied). The input file `candidates.md` is the candidates document, pretty-printed (two-space indent, one key or array element per line), every non-ASCII code point written as a `\uXXXX` escape, wrapped in a fence `<untrusted source="ticket-queue-input" id="<R>">` ... `</untrusted id="<R>">` with `<R>` a fresh random 16 hex characters, every `</untrusted` and `<untrusted` in the content (any letter case) neutralized as `&lt;/untrusted` and `&lt;untrusted`, and the closing fence on a line of its own at the end. The size is measured on the escaped document. Over 64 KiB, candidates are dropped from the bottom until it fits (`candidates_dropped` in the result and the log). With the per-field caps no line can exceed 16 KiB; `input_invalid` remains as a guard.

The default skill, `ticket-queue:rank-tickets`, is bundled in `plugin/` (a Claude Code plugin named `ticket-queue`). It reads the prompt file named in its first message, reads the input from the path in the session's context line, joined with the session directory of its first message, with the Read tool (never Glob, never Bash), reads to the closing fence or fails, ranks the candidates against the board's goals, prioritized epics and the deterministic scores, writes `ranking.json` with the Write tool into the session's artifacts directory following the schema in the prompt file, and copies the `skill_marker` value from its own reference file `references/marker.md` into the artifact. It gives no report or escalation instructions (design guide §11): `exec` appends the report rules, and the trusted prompt file says to report `done` with `--artifact ranking.json` and an inline `--summary`, using the absolute path of claude-session; the profile allows Bash only for `claude-session report` and denies its file forms (`--summary-file` and `--reason-file`). The marker is read at run time from the installed `references/marker.md` (trailing newline stripped), which is opened without following links, must be a regular file of at most 256 bytes, and is `launch_failed` when absent or empty after stripping; `rerank.marker` defaults to it (see the marker rule below). The plugin directory ships the four sandbox placeholders (`.claude/` carrying a `.gitkeep`, `.mcp.json`, `CLAUDE.md`, `CLAUDE.local.md`) and the bundled permission profile `plugin/profiles/rank.yaml`, a copy of claude-session's built-in `readonly` profile that **denies** `Agent` and `Task` (and allows only `Skill(ticket-queue:rank-tickets)`, `Read`, `Write`, `Edit` under the generated rules and `Bash(claude-session report:*)`, while denying `Bash(claude-session report * --summary-file *)`, `Bash(claude-session report * --reason-file *)` and the absolute-path forms of both; the exact wildcard syntax is a live-test item in `docs/design.md`). Output validation is code: the schemas are not read at run time, and a test checks the code against them. `plugin.json` keeps the version `0.0.0`, and a packaging test asserts the four placeholders in the installed package. The bundled plugin directory gets the same checks as a custom one (below).

A custom skill is selected with `rerank.skill` and, when it lives in another plugin, `rerank.plugin_dir` (default null, the bundled plugin), which is passed with `--plugin-dir` and hashed into the input hash. Both the bundled and a custom plugin directory must have no directory or file writable by group or others and must be owned by the user or root, else the run fails `launch_failed`. It must follow the same contract (input, artifact name, schema, run id echo). **Marker rule.** With the bundled implementation, the output must contain `skill_marker` equal to the effective `rerank.marker` when that is not null, and must not contain it when null. `rerank.marker` defaults to the bundled reference value when `rerank.skill` is the default and `rerank.plugin_dir` is null, else to null (the check is then the run id only). A custom `rerank.command` must not print `skill_marker`. The marker detects a skill that did not run; it is not authentication. The plugin directory hash walker follows no symlinks, accepts only regular files and directories, at most 500 files and 4 MiB in total, else `launch_failed`. `validate` also checks a custom plugin directory: the four placeholders exist and are empty (`.mcp.json` equals `{}`, `CLAUDE.md` and `CLAUDE.local.md` are empty, `.claude/` holds no hooks or settings), there is no `hooks/` or `agents/` directory, `plugin.json` has no `hooks`, `mcpServers` or `commands` key, and `skills/<skill name>/SKILL.md` exists.

`validate --probe` runs one real re-rank on a built-in sample of three fake tickets and reports `probe_ok`, `sandbox_active`, the duration and the cost; `validate` without `--probe` checks the config, resolves the skill, the plugin directory (the checks above) and the profile file (it warns `profile_skill_mismatch` when the profile's `Skill` rule does not name `rerank.skill`), and runs `ticketctl --version`, `claude-session --version` (only when the global `rerank.enabled` is true and `rerank.command` is null; otherwise that check is reported `ok` with the message `not needed`), and `whoami` and `fields check` per configured site, without a model call. `--dry-run` of a launch is not a self-test: it reports a healthy sandbox for setups in which every report call still fails (a missing placeholder, an interpreter reachable only through an alias).

### Claims

A claim reserves a ticket so it is not handed out twice. It is local: it never writes to the ticket system. A claim has: `(site, key)` (unique per ticket), `claimed_at`, `renewed_at`, `expires_at`, `ttl_s`, an optional `holder` and labels, and `claimed_key` (see Claim state below); the claim's `board` is the ticket's current owner (not stored on the claim). `consecutive_failures` is kept on the ticket, not the claim, across claims.

`holder` is an explicit opaque string (`--holder`), never inferred from the caller; it matches the holder grammar. Labels follow the usual `--label key=value` rule (a multiset; adding an identical pair is a no-op); a claim has at most 16 label pairs and 2 KiB of labels in total, and more exits 2 `invalid_argument`, reason `too_many_labels`. A caller holds a claim when both holders are present and equal. A claim without a holder is never renewed (`claim KEY` on it exits 20 `refused`, reason `claimed`); `release KEY` without `--holder` ends it. A claim with a holder is released only with the same `--holder` or `--force`.

**Taking a claim** (`claim KEY`, `next --claim`) follows these steps:

1. Resolve the key and site (see [Identifiers](#identifiers)).
2. Read the ticket live with `ticketctl get` (the fields of [refresh](#refresh) step 1 plus `description`). Not found: a key not stored exits 10 `not_found`; a stored key is marked gone and exits 20 `refused`, reason `gone` (`next --claim` passes over it).
3. Canonicalize a moved key.
4. In one `BEGIN IMMEDIATE` transaction: store the fresh ticket through the writer; evaluate the rules on it with the live claim, skip, pin and hidden state at `now` (the hard rules for `claim KEY` and for pinned tickets, all rules for `next --claim`; a holder's renewal is refused only for `gone` and `hidden`, see below); a live claim by another holder refuses (`claimed`); write or renew the claim; write the outbox event; commit.
5. `SQLITE_BUSY` after the busy timeout retries steps 2 to 4 once, then exits 12 `unavailable`, reason `contended`.

`claim KEY` on an explicit key refuses only on hard rules: exit 20 `refused` with reason `done`, `gone`, `skipped`, `hidden` or `claimed` (held by another holder or by a caller without a holder). Each soft rule that fails or is unknown on the fresh ticket adds a warning `soft_rule_overridden` with `rule` set, because naming a ticket is the user's intent (a named claim overrides the soft rules as a pin does); a key outside every board's pool is allowed. A holder's renewal (`claim KEY` by the claim's holder, and `claim KEY --renew`) sets `expires_at` to `now` plus `--ttl`, else the claim's stored `ttl_s`, adds labels and reports `renewed: true`, which tells the caller it already held a live claim on the ticket. A renewal succeeds when the ticket is now `done` or skipped, with the warnings `ticket_done` and `ticket_skipped`, and is refused only for `gone` and `hidden` (exit 20 with that reason); a `reassigned` ticket renews with the warning `reassigned`. A new claim still refuses every hard rule. `claim KEY --renew` renews only: with no live claim held by this holder it exits 20 `refused`, reason `not_held` (the idiom for periodic renewal), and without `--holder` it exits 20 `refused`, reason `not_held` (a caller without a holder holds nothing). A claim held by a different holder exits 20 `claimed`.

**TTL.** A claim is live while `expires_at > now`; `claim.ttl` (default 72 hours; `--ttl` per claim, at most `claim.max_ttl`, default 30 days) applies to a claim that is not renewed. `--ttl` is rounded up to whole seconds; below 1 second or above `claim.max_ttl` exits 2 `invalid_argument`. A renewal with `--ttl` replaces the claim's `ttl_s`. A renewal reads the ticket live like a new claim; when ticketctl is unavailable it exits 12 and the claim keeps its `expires_at`, so a caller renews well before the TTL ends (for example at half of it). The [housekeeping sweep](#store) ends lapsed claims. Read commands never write. A same-holder `claim KEY` on a lapsed claim creates a new claim (`renewed: false`). `prune`'s `dead_grace` release re-checks inside its transaction.

**Release.** `release KEY [--failed] [--holder H] [--force]` is idempotent: releasing an unclaimed ticket exits 0 with `unchanged: true`. A holder that differs from the claim's exits 20 `refused`, reason `holder_mismatch`; only a human `--force` (actor `human:`, see [Commands](#commands)) overrides it. A normal release sets the ticket's `consecutive_failures` to 0. A failure is counted when `release --failed` ends a live claim (by its holder, a holderless release or `--force`); on an unclaimed ticket it is `unchanged` and counts nothing. It adds 1 and records `last_failure_at` (shown by `why`); the auto skip is created when the count is at least `claim.max_failures` (default 3; a lowered limit applies at the next failure), in the same transaction that ends the claim, with `source: auto` and a reason, replacing an existing skip (a ticket has at most one skip), and `post-release` is written before `post-auto-skip`. The skip lasts until `unskip`. An `unskip` that ends a skip resets the count to 0; a lapse or a `prune` release leaves it unchanged.

**Claim state.** A claim stores `claimed_key`, the key its `claim` or last renewal resolved to at that time. `claims` and `list --claimed` report `ticket_state` for each claim: the first that holds of `gone`, `done`, `reassigned` (the assignee is neither the site's account nor empty), `moved` (`claimed_key` is now an alias of the canonical key) and `ok`. A renewal under the canonical key sets `claimed_key` and so ends `moved`. A refresh never releases a claim. `prune` releases a claim whose ticket has been `done` or `gone` for more than `claim.dead_grace` (default 7 days, counted from `state_since`), with a log entry; this is the only automatic release besides a lapsed TTL. A claim never excludes the ticket from `show` or `why`.

`claims` lists live claims ordered by `claimed_at`, filtered by `--holder`, `--label k=v` (repeatable, all must match), `--board` and `--site`. An entry is `{site, key, requested_keys, board, holder, labels, claimed_at, renewed_at, expires_at, expires_in_s, ttl_s, ticket_state, ticket: {title, status, url}}`; `ticket` is never null. A hidden claimed ticket's entry is `{site, key, requested_keys, hidden: true}`. `count` includes hidden entries, and every entry, hidden or not, is in `claimed_at` order.

### Manual order

**Pins.** The pin list is an ordered, global list of tickets above all scoring and re-rank (`list --board B` shows the pinned tickets B owns, see [Commands](#commands)). `pin KEY` appends the ticket (`--top` puts it first); `--expires D` sets an expiry. `pin` and a pinning `move` of a ticket that no enabled board's pool holds exit 20 `refused`, reason `not_in_pool`; `pin` of a done or gone ticket exits 20 with that reason. A `pin` of a pinned ticket is `unchanged`, except that `--top` moves it first and `--expires` replaces the expiry. `unpin KEY` removes it. `move KEY` takes `--to N` (1-based), `--top`, `--before KEY` or `--after KEY` (the anchor must be pinned) and reorders within the pin list, pinning the ticket first when it was not pinned; `--to N` places at N (N larger than the list: last; N below 1: exit 2), and an anchor equal to the ticket exits 2. `pin_position` is a ticket's index in the pin list (it is never called `position`, which only means the ranking), renumbered 1..n after every change. A pin has no timer unless `--expires` is given, and it is kept through a normal release. A pin of a ticket that is in no enabled board's pool is **dormant**: it stays stored with its `pin_position`, is never handed out (no enabled board owns it), `why` and `list --all` show it as `pinned` with state `dormant`, and the pin object carries `dormant: true`. A dormant pin is dropped only by `--expires`, a ticket that is `done` or `gone`, `unpin`, or `prune` (`pin_dropped`, reason `retention`) `retention.tickets` after the ticket's `last_seen` while it is in no pool; a ticket that returns to a pool makes its dormant pin live again at its old `pin_position`. The [housekeeping sweep](#store) drops expired, done and gone pins; until then a pinned ticket that fails a hard rule (a hidden ticket included: its pin is kept) is `pinned_blocked`: it stays stored, is shown with its reason, and is never handed out (`why` and `list --all` warn `pinned_blocked`). A pin or a named claim overrides the soft rules; `why` lists each overridden soft rule as a warning (`soft_rule_overridden`).

**Skips.** `skip KEY [--for D|--until T] [--reason-file F]` removes the ticket from candidates. A skip with no time lasts until `unskip KEY`; a timed skip ends by itself (`until` is an RFC 3339 instant). `--for` with `--until`, or a time not after `now`, exits 2 `invalid_argument`. `skip` of a skipped ticket replaces the skip (source `human`, the new time and reason; `unchanged: false`); the failure count is not touched. `unskip` of a ticket with no live skip is `unchanged` and leaves the count; an `unskip` that ends a skip resets it to 0. `source` is `human` or `auto`; an auto skip comes from `release --failed` (see [Claims](#claims)) and never times out. `--reason-file` text is untrusted and shown sanitized. `list --skipped` lists both kinds. A skipped ticket fails the hard rule `skipped`.

Pin, move and skip changes are written to `log.jsonl` with the actor. They are not external actions and have no audit record.

### Query language

One engine, in one UI-free module, serves `list --query`, `next --query`, the TUI panel, `browse.query` and the quick presets. A query is text of at most 1000 characters (a word at most 200, nesting at most 20, at most 50 conditions, an `IN` list at most 50 entries); control characters are refused; there is no eval and no regex (`LIKE` uses an iterative matcher). It narrows the stored pool and never widens it. A syntax error exits 2 `invalid_argument` with `reason: bad_query` and the position.

Grammar: `expr := term (OR term)*`; `term := factor (AND factor)*`; `factor := NOT factor | '(' expr ')' | condition | boolean-field`; `condition := field op value | field IN '(' value (',' value)* ')' | field NOT IN (...) | field IS [NOT] NULL | field [NOT] LIKE string`; ops `= != <> < <= > >=`; `query := [expr] [ORDER BY key [ASC|DESC] (',' key [ASC|DESC])*]` with at most 8 keys. Keywords and field names are case-insensitive. A string is single-quoted with `''` for a quote. A duration is `[0-9]+w`, `d`, `h`, `m` terms each used at most once in that order (`1w2d`, `90m`, `12h30m`), and a literal may be negative (`-2d`); a number matches `-?[0-9]+(\.[0-9]+)?` (no exponent, no `+`); a number compared with a duration field exits 2 `bad_query`. `me` (unquoted) is the account id of the ticket's own site and matches `assignee` and `reporter`; text comparison of `assignee` uses `display_name`; `'me'` is text. `true` and `false` are booleans. An unquoted word that is not a keyword, field, `me`, `true` or `false` exits 2 `bad_query`.

| Field | Type | Notes |
|---|---|---|
| `key`, `project`, `title`, `status`, `category`, `type`, `priority`, `assignee`, `reporter`, `epic`, `parent`, `sprint`, `board`, `holder` | text | `category` is the status category; `epic` and `parent` compare their keys; `sprint` the names of the ticket's sprints (any); `holder` the claim's holder |
| `labels`, `claim_label` | set of text | `labels = 'x'` means the set contains `x`; `!=` means it does not; `IN (...)` means it contains any; `LIKE` matches any member; `claim_label` is the claim's labels as `k=v` |
| `text` | free text | `LIKE` only; over `title`, `key` and `labels` (matches when any matches) |
| `estimate`, `score`, `position`, `rerank_position`, `failures` | number | `score` is the effective score, `failures` the consecutive failed releases; `position` is the position in the full order of the selected boards before the query; an ineligible ticket has none (known absent) |
| `age`, `updated`, `due` | duration | `age` since created, `updated` since last update, `due` the due date minus today's UTC date, in whole days, as a duration (the `d` of [Scoring](#scoring); negative when overdue) |
| `mine`, `pointed`, `blocked`, `claimed`, `pinned`, `skipped`, `eligible`, `overdue` | boolean | usable bare (`claimed`, `NOT blocked`); `mine` is `assignee = me`, `pointed` and `blocked` read the raw fields with the rule's unknown cases, `overdue` is `due < 0d` |

Text `=`, `!=`, `IN` and `LIKE` are ASCII case-insensitive for every text field. `LIKE` uses `%` and `_` with `\` as the escape. Evaluation is three-valued (Kleene logic, as in SQL). A known absent value (unassigned, no due date, no epic or parent, no sprint, empty labels) is null: `=` is false, `!=` is true and `IS NULL` is true. An unknown value (named in `incomplete`, or not loaded) makes a condition on it unknown and `IS NULL` true; `NOT unknown` is unknown; a row is kept only when the whole expression is true. `me` for a ticket whose site has no stored account makes the condition unknown. `NOT text LIKE p` is the negation of `text LIKE p`. `position` of an ineligible ticket is known absent: `position < 5` is false and `position IS NULL` is true. `sprint != 'x'` is `NOT sprint = 'x'`. `ORDER BY` defaults to `ASC`; text sorts ASCII case-insensitive, numbers and durations by value. `ORDER BY` accepts scalar fields only (not `labels`, `text`, `claim_label`); booleans sort false before true; a repeated key exits 2 `bad_query`; an unknown value sorts last in both directions, and ties end on `(site, key)`. `eligible` is never unknown for a stored ticket. A key that is not a field exits 2 `unknown_field`.

Bounds: each `NOT` counts toward nesting 20; a `LIKE` pattern is at most 64 characters with at most 4 `%`; compared text is its first 512 characters; an evaluation budget of 100,000 character comparisons per row (summed over the row's `LIKE` conditions) applies, then exit 2 `invalid_argument` with reason `too_expensive` (the TUI shows the error and evaluates off the UI thread).

The **named order** `position` is the ranked order of [Ordering](#ordering). Quick presets of the query panel are query texts: `m` mine (`mine`), `d` due soon (`due < 7d`), `b` blocked (`blocked`) and `c` claimed (`claimed`); they work inside the panel only.

### Concurrency

Commands run by cron or the harness are safe under concurrent invocation. The store uses WAL and a 5-second busy timeout. `refresh` and `rerank` take a per-board lease (holder PID and process start time, plus an expiry); a second caller exits 0 and reports "already running" for that board. A lease expires 120 seconds after its last heartbeat (every 30 seconds); a holder is dead when its PID is gone or its start time differs, and a lease whose holder is dead may be taken over. A claim is one `BEGIN IMMEDIATE` transaction in which every check is re-run and the claim row (unique per ticket) is the arbiter. `next`, `list`, `show`, `why`, `claims` and `browse` never wait for a refresh: they read the last committed rows.

### Hook delivery

Post-hooks are delivered through an outbox: every event is written to the store in the transaction that caused it, with an `event_id`, a `seq` and one row per hook entry, and delivered at least once after the commit. An event is written only for a hook name with at least one entry. Each row records the sha256 of its entry's `cmd` and is delivered by the current entry with that hash (with that entry's current `timeout` and `async`); when no entry has that hash any more, the row ends with a final `hook_failed` record (`final: true`). Writing commands and `refresh` deliver after their output is written and stdout and stderr are flushed and closed. The budget (at most 10 deliveries and 5 seconds per command; `refresh`: 30 seconds) bounds the whole delivery phase: a synchronous delivery starts only while at least 1 second remains and runs with the timeout `min(entry timeout, remaining budget)`; a delivery cut by the budget is a failed attempt. After an entry fails once in a command, its other events wait for a later command. Inside the delivery phase the SQLite busy timeout is `min(5 s, remaining budget)`, and a lock failure counts as a failed attempt. A hook's process group (created by ticket-queue) is signalled on timeout before its leader is reaped. A delivery first takes the event's lease (`lease_until = now + effective timeout + 5 s`) in a transaction, so two processes never run the same delivery at once. A delivery succeeds when the hook exits 0 within its timeout. A failure retries with backoff from 1 minute doubling to 6 hours. Read commands never deliver. An `async` entry counts as delivered once started; its failures are not retried, and a receiver that can take more than a few seconds should use `async: true`. `release --failed` writes `post-release` before `post-auto-skip`; delivery order is not guaranteed, and consumers order by `seq` (gaps in `seq` are normal: one counter serves log records and events). A receiver deduplicates on `event_id` and tolerates unknown payload keys. A failed attempt is logged (`hook_failed`) and never fails a command. An event still undelivered after `retention.events` (14 days) is deleted by `prune` with a final `hook_failed` log record (`final: true`). `boards` and `validate` report `undelivered_events` meanwhile, and `validate` reports undelivered events whose hook-entry hash matches no configured entry (warning `orphan_events`).

## `--json` outputs

Schemas live in [schemas/cli/](../schemas/cli/). Every output is a JSON object (never a bare array; `export` prints JSON lines, exempt from this rule, each validated by `log.json`), validated against its schema in tests. Each command's fields are in its schema. `list`, `show`, `why`, `next`, `claims` and `boards` carry `refreshed_at` and `stale` (see [Store](#store)); state-changing outputs do not. `list`, `show`, `why`, `next`, `claims`, `boards`, `refresh`, `claim` and `rerank` carry `complete` (false when a selected board is failed, disabled or truncated) and `errors`. Every output except the error envelope, `browse-result.json`, `cron install` and `cron uninstall` carries `warnings` (command-level warnings such as `browse_query_invalid`, `refresh_partial`, `scan_limit_reached`, `soft_rule_overridden`, `ticket_done`, `ticket_skipped` and `reassigned`; board warnings stay in `boards[].warnings`). Multi-board outputs carry `boards`, each with a `status`: `ok`, `refresh_failed`, `truncated`, `disabled` (the last refresh failed with a configuration error, the config row of the failure table) or `excluded` (`enabled: false`); `rerank_disabled` is never a board status. A board's `pool` counts its member rows and `eligible` counts the candidates it owns. A board's `rerank` is `off` (re-rank not enabled for the board), `none` (enabled, no result), `ok` (a valid result applies), `expired` or `failed` (the last run failed; the deterministic order applies). Ticket text fields (`title`, `description`, `labels`, `epic.title`, `parent.title`, display names, reasons) are `x-untrusted` in the schemas and printed sanitized. Timestamps are UTC `YYYY-MM-DDTHH:MM:SSZ`.

The set of fields of a ticket object follows ticketctl's normalized ticket (`key`, `site`, `requested_keys`, `url`, `title`, `type`, `status`, `assignee`, `reporter`, `priority`, `estimate`, `sprints`, `parent`, `epic`, `labels`, `due_date`, `created`, `updated`, `blocked`, `incomplete`) plus ticket-queue's own `board`, `score`, `position`, `rerank`, `eligible`, `verdicts`, `claim`, `pinned`, `skipped` and `warnings`. `board`, `score` and `position` are null for a ticket in no pool; `rerank` is `{applied, position, excluded, reason, age_s}`; `verdicts` is an object keyed by rule name, each `{result: pass|fail|unknown, reason, overridden_by_pin}`; `claim`, `pin` and `skip` are the objects or null, and `pinned_blocked` is `pin.blocked`. `description` is printed only by `show` (with `description_read_at`). Warning codes are the `warning_code` enum of `defs.json`; each is defined where it is emitted.

Additive changes (new optional fields) are allowed within a minor version; removals and renames are breaking (design guide §13).

## Hooks

Post-hooks only in 0.x (no `pre-` hooks; a `pre-claim` hook is a 1.x item). Hooks are configured in `hooks:` (design guide §8): each entry is `{cmd, timeout, async}` (timeout: integer seconds 1 to 600 or a duration, default 30 seconds), run via `sh -c` in its own process group with the JSON payload on stdin and `TICKET_QUEUE_HOOK`, `TICKET_QUEUE_ID` and `TICKET_QUEUE_OBJECT_TYPE` in the environment (`TICKET_QUEUE_ID` is the payload's `object_id`); the hook's environment is the tool's environment minus the names in `ticketctl.pass_env` and `claude_session.pass_env`. An unknown hook name is `invalid_config`. Payloads (schemas in `schemas/hooks/`) carry the common keys `tool`, `hook`, `event_id`, `event_ts`, `seq` (monotonic per store), `object_type` (`ticket` or `board`), `object_id` (`<site>:<KEY>` or the board name), `board`, `key`, `site`, `holder`, `labels` (array of `k=v`) and `requested_keys`; ticket hooks carry the ticket's owner board in `board` (null when it has none), and board hooks carry the board name in `board`, null `key`, `site` and `holder`, and empty `labels` and `requested_keys`; no payload carries ticket text. Payloads omit `repo` (ticket-queue has no repository notion), so a gate matching on a payload lands in scope `*`. Delivery is described under [Hook delivery](#hook-delivery).

| Hook | Fires | Notes |
|---|---|---|
| `post-claim` | after a new claim is written, or a renewal that adds a label (`claim`, `next --claim`); a plain renewal fires nothing (the log keeps it) | `renewed`, `claimed_at`, `expires_at`, `ttl_s` |
| `post-release` | after a claim ends by `release`, a lapsed TTL, `prune`, `--force` or a merge | `failed`, `reason` (`released`, `lapsed`, `pruned`, `forced`, `merged`), `forced`, `actor`, `claimed_at`, `consecutive_failures` |
| `post-auto-skip` | after `release --failed` reached `claim.max_failures` | `skip_source`, `failures`, `caused_by` (the `post-release` event id) |
| `post-refresh` | after a refresh in which a board's status or error code changed (recovery included) or a claimed ticket's state changed (either direction), and at most once per `hooks.refresh_repeat` (default `6h`) while a board stays failed | `boards[]` `{board, status, previous_status, error_code, lower_code, retry_after}`; `changed_claims[]` `{key, site, holder, labels, requested_keys, ticket_state, previous_state}` |
| `post-rerank` | after a re-rank run failed (automatic skips are log-only) | `outcome: failed`, `reason` from the table, `run_id` |

## Config

YAML at `~/.config/ticket-queue/config.yaml` (respecting `XDG_CONFIG_HOME`), plus `config.d/*.yaml` drop-ins merged in lexical order after it (maps merge, hook lists append, every other list replaces). Boards are ordered as written in `config.yaml`, then boards first defined in drop-ins, in lexical file order; a drop-in that overrides an existing board keeps its slot. The schema is [schemas/config.json](../schemas/config.json); `config.example.yaml` documents every key and its default. Invalid config fails fast naming the key (exit 2 `invalid_argument`, reason `invalid_config`); a board with no `site` and no `ticketctl.default_site` is `invalid_config` naming the board. Unknown keys and duplicate mapping keys are `invalid_config`. Structured config (`boards`, `hooks`, maps) cannot come from the environment; only top-level and nested scalars can, and a scalar from the environment is parsed as a YAML scalar (`true`, `5`, `30m`). Precedence: flags, then `boards.<name>`, then environment variables, then global config with drop-ins, then built-in defaults; the global `rerank.enabled` is a gate for every board. ticket-queue has no notion of a repository, so the board takes the per-repo position of the precedence order (design guide §5). Epic and parent keys are case-insensitive and stored upper-case. Structured `labels` of a source must all match; the other lists match any.

## Environment variables

Config values from the environment are named `TICKET_QUEUE_<KEY>` (upper-cased, nested keys joined with `__`, e.g. `TICKET_QUEUE_REFRESH__STALE_AFTER`). The hook variables are `TICKET_QUEUE_HOOK`, `TICKET_QUEUE_ID` and `TICKET_QUEUE_OBJECT_TYPE`; these three names are never config keys. ticket-queue reads no credentials: ticketctl's own variables are named in ticketctl's config, and ticket-queue hands them to the ticketctl child only when they are listed in `ticketctl.pass_env`; claude-session children get only `claude_session.pass_env` (never ticketctl's names). `XDG_CONFIG_HOME` and `XDG_STATE_HOME` are respected.

## Trust boundary

Allowing ticket-queue allows what its config can do: hooks, `rerank.command`, `rerank.permission_profile` (a custom profile can allow Bash or Agent for a hostile-input session), `rerank.plugin_dir` (a plugin's hooks and MCP servers run outside the sandbox), `rerank.setting_sources` (`user` brings the user's own hooks and permissions in), `rerank.env_allowlist`, `claude_session.pass_env`, cron with `cron.env_file`, and `ticketctl.config` with `pass_env`; the scalars among these (for example `TICKET_QUEUE_RERANK__PLUGIN_DIR` and `TICKET_QUEUE_RERANK__PERMISSION_PROFILE`) can also come from `TICKET_QUEUE_*` environment variables. A constrained caller must fix `--config`, scrub the environment and allow only `list`, `show`, `why`, `next` without `--claim` and without `--refresh` (`--refresh` calls ticketctl, writes the store and runs hooks), `claims`, `boards` and `export`. Hook environment stripping is a boundary only when the caller cannot choose the config. A holder is not a secret or an authentication: `claims` prints every holder, and a caller allowed `release` can end any claim whose holder it can read. The `--force` TTY test guards against accidents; a caller that can run a command in a pseudo-terminal passes it. `ticketctl` and `claude-session` are resolved on `PATH`, like the siblings; there are no binary-path keys.

Files read from user-supplied paths (`--query-file`, `--reason-file`, `goals_file`, the config file and drop-ins) are opened with `O_RDONLY|O_NONBLOCK|O_NOFOLLOW|O_CLOEXEC`; `fstat` must show a regular file (a FIFO never blocks), then non-blocking is cleared; a file whose opened descriptor resolves (`/proc/self/fd/N` on Linux, `F_GETPATH` on macOS, `realpath` otherwise) under `/proc`, `/sys` or `/dev` is refused; at most the cap plus one byte is read, more is an error, and stdin `-` is capped the same way; the text is strict UTF-8 (caps: a query 4 KiB, a reason 4 KiB, goals 16 KiB, each config file 256 KiB); errors never echo content. These are ticketctl's reader rules. `--reason-file` reads any file the caller can read, and `why` and `show` print the stored text sanitized. Loading refuses a config file, a `config.d/` directory or a drop-in that another user owns or that group or others can write (exit 2 `invalid_argument`, reason `unsafe_path`; the check the env file also gets), and refuses a symlinked config file on purpose (the error names the link). YAML (the config file, the drop-ins and the `config.d` default-query file alike) is loaded by scanning the event stream first: it refuses an anchor, an alias, any tag other than the core ones, a scalar key `<<`, a duplicate mapping key and nesting deeper than 20, resolves only str, int, float, bool and null (no `.nan`, `.inf`, timestamps, binary, sets or sexagesimal numbers), and maps every parser exception, `RecursionError` included, to exit 2 `invalid_argument`, reason `invalid_config`.

## Files

State is under `~/.local/state/ticket-queue/` (respecting `XDG_STATE_HOME`).

| File | Public | Content |
|---|---|---|
| `state.db` | no | SQLite (WAL), versioned, additive-only migrations: tickets, board membership, aliases, accounts, boards, claims, pins, skips, rerank results, events outbox |
| `log.jsonl` | yes | append-only operational log, schema [schemas/log.json](../schemas/log.json) |
| `tmp/<run_id>.lock`, `tmp/<run_id>/` | no | a re-rank run's lock file and its private directory (mode 0700) with the input and prompt files, deleted when the run ends |
| `cron.lock`, `crontab.previous` | no | the lock around the crontab read-modify-write and the previous crontab text (mode 0600) |

There is no `audit.jsonl`: no command takes an external action. `--actor` and `--decision-id` are accepted and recorded in `log.jsonl`. [schemas/audit.json](../schemas/audit.json) is kept as an empty contract for tools that read every tool's audit file.

The store keeps, for each ticket, the normalized object as ticketctl returned it (sanitized by ticketctl), with `description` (from the last `get`) cut to 8 KiB, and no verdicts or scores. It holds ticket text on disk; it is mode 0600 in a 0700 directory. `prune` drops the pin of a ticket that has been in no pool for `retention.tickets` from its `last_seen` (`pin_dropped`, reason `retention`), removes tickets with no member row, no claim, no pin and no live skip after `retention.tickets` from `last_seen`, tombstones that are not claimed, pinned or under a live skip (with their member rows), aliases whose target row is gone, expired re-rank results, outbox events after `retention.events` (an undelivered one with a final `hook_failed` record), leftovers of crashed re-ranks (see [Slot contract](#slot-contract)) and claims as described under [Claims](#claims); `log.jsonl` is kept (rotated by size under a lock, never pruned). `cron install` also schedules `prune` daily.

## Audit and log

`log.jsonl` records: `refresh` (per board: counts, status, duration), `claim`, `release`, `auto_skip`, `pin`, `unpin`, `move`, `skip`, `unskip`, `pin_dropped`, `rerank` (outcome, reason, run id, duration, cost when known, `sandbox_active`, `candidates_dropped`), `rerank_skipped`, `prune` and `hook_failed`. Every record has `seq` (monotonic per store, one counter shared with the outbox events), `ts`, `event`, `actor`, `actor_source`, `decision_ids`, and `event_id` when an outbox event exists; ticket records add `labels` and `requested_keys`. Every log record is written inside a write transaction: its `seq` is allocated as one more than the larger of the stored counter and the last `seq` in the tail of `log.jsonl` (read under the same write lock), the line is appended to `log.jsonl` and flushed, then the transaction commits; rotation happens inside the same transaction. The log is opened by path inside every transaction (`O_APPEND|O_NOFOLLOW`, the opened inode compared with the path's) and is never kept open between transactions, so another process's rotation is seen. File order therefore equals `seq` order and `export --after-seq N` is a safe cursor. After a crash a record can describe a change that was rolled back: the orphan line keeps a unique `seq` and the gap is normal, a consumer may see a record for a rolled-back change, and the outbox, not the log, is the source of truth for events. A lapse is a `release` record with reason `lapsed`; `release.reason` is `released`, `lapsed`, `pruned`, `forced` or `merged`; `pin_dropped.reason` is `done`, `gone`, `expired` or `retention`; a `skip` records its reason as a byte count; `hook_failed` is `{event_id, hook, attempts, final}`; `level` is optional. None holds ticket text beyond keys. [schemas/log.json](../schemas/log.json) defines them; `decision_ids` appear only in the log.

`export [--since T] [--after-seq N]` prints JSON lines (exempt from the one-object rule, each validated by `log.json`), reading rotated files oldest first. `T` is RFC 3339, a date or `<n>m|h|d|w`. `--since` and `--after-seq` together return records matching both; an invalid value exits 2 `invalid_argument`. Records in rotated-away files are gone; a gap in `seq` is not proof of loss.

## Cron

`cron install [--interval D]` writes one block in the crontab (default interval 15 minutes). Accepted intervals are `1m`, `2m`, `3m`, `4m`, `5m`, `6m`, `10m`, `12m`, `15m`, `20m`, `30m`, `1h`, `2h`, `3h`, `4h`, `6h`, `8h`, `12h` and `24h`; any other exits 2 `invalid_argument`, reason `invalid_interval`, listing them. Minutes write `*/N * * * *` (`1m` writes `*/1 * * * *`), hours `0 */N * * *`, and `24h` writes `0 0 * * *`; `prune` runs `17 3 * * *`. Schedules are in the machine's local time. The block is: the first line `# ticket-queue managed v1 every=<interval>` (recording the accepted value), a `PATH=<dirs>` line, the refresh line `<schedule> { [ -O '<env_file>' ] && [ ! -L '<env_file>' ] && . '<env_file>'; } || { echo 'ticket-queue: env file guard failed' >&2; exit 1; } && '<absolute ticket-queue>' refresh --quiet` (the env-file guard only with `cron.env_file`; a failed guard is loud: cron mails the message and the line exits 1), the daily `prune --quiet` line, and the last line `# ticket-queue managed end`. `PATH=` lists, deduplicated in this order, the directories of `ticket-queue`, `ticketctl` and `claude-session` as `shutil.which` finds them at install (a missing one is skipped), then `/usr/local/bin:/usr/bin:/bin`. Every entry must be absolute, owned by root or the user and not writable by group or others, else install exits 2 `invalid_argument`, reason `unsafe_path`. `<absolute ticket-queue>` is `shutil.which("ticket-queue")`, else `sys.argv[0]`, made absolute without resolving links; in both cases its directory gets the same ownership and mode check as the `PATH=` entries. A reinstall with a different interval or path replaces the block (`changed: true`).

Install refuses a path containing any character outside `[A-Za-z0-9_@+=:,./-]`, a `cron.env_file` that is not an absolute path, and an env file that is not a regular file owned by the user with mode 0600 or 0400 in a directory others cannot write (`validate` repeats the checks). A block starts at a line matching `^# ticket-queue managed v[0-9]+ every=\S+$` and ends at the line `# ticket-queue managed end` exactly. `crontab -l` runs with `LC_ALL=C`; exit 1 is an empty crontab only when its stderr contains `no crontab for`, and any other failure exits 12 `lower_failed`. Install and uninstall take a lock (`cron.lock` in the state directory) around the read-modify-write and keep a copy of the previous crontab text in the state directory (`crontab.previous`). `cron uninstall` removes a block only when every line inside it is in the tool's own formats (the header, `PATH=`, the refresh line, the prune line); when other lines sit inside it, it refuses with exit 12, reason `unsafe_block`, and changes nothing. For a block without its end line (written by another program) it removes the header and only the directly following lines in the tool's own formats, and a `PATH=` line is matched only with the exact generated value (absolute directories ending in `/usr/local/bin:/usr/bin:/bin`). The harness writes the same block by these rules.

## TUI

`ticket-queue browse` is an optional Textual interface (the `ticket-queue[tui]` extra; without it the command exits 12 `tui_missing` and names the install command). Flags: `--focus KEY`, `--board B`, `--interval D` (wins over `browse.refresh_interval`) and `--result-file PATH`.

**List.** One table over all boards or one board (`tab` switches). Columns: `key` (cut from the left), `note` (`[refreshing]`, `[stale: <code>]`, `[changed]`), `score`, `pos`, `title`, `status`, `pri`, `est`, `sprint`, `age`, `flags` (`P` pinned, `C` claimed with holder, `S` skipped, `R` re-ranked, `!` warning). `[stale: <code>]` shows the board's `lower_code` or `error.code`; `[changed]` is set when `updated` differs from the last shown value and cleared when highlighted. Every cell is cut to its width in terminal cells and by code points (at most 4 per cell), runs of more than 3 combining marks become one marker, and empty cells stay as padding. The header is sticky with a sort arrow; left and right (or `h` and `l`) scroll by column with `key` and `note` pinned; the offset survives refreshes. Sorting is by parsed value (unknown last in both directions), the header cursor (`H`) sorts on enter or space and reverses on a second press, and the ranked order is the default preset (`ORDER BY position`). At 10 columns only `key` is shown.

**Query panel (`F`).** A form and a query line kept in sync, with match counts and unknown counts and the actions Apply, Cancel, Reset and Reset to default. `D` writes the current query as the default into `config.d/` next to the resolved config file (so `XDG_CONFIG_HOME` is respected), as `90-browse-query.yaml`, through the temp file `config.d/.90-browse-query.tmp` (mode 0600, not matching `*.yaml`, written with a safe dumper) and a rename; stale temp files are deleted at start; the directory must be owned by the user and not writable by group or others, else `D` shows an error; the path is shown in the status line, and the file overrides `browse.query` in `config.yaml`. History is kept in `~/.local/state/ticket-queue/browse-history` (mode 0600, valid queries only, newest first, no duplicates, at most 100 lines of 1000 characters, each re-validated on load, saved by temp file and rename, merged with entries other running instances saved; when another instance holds the history lock the save is dropped). A bad `browse.query` is a warning and is ignored, so it never fails other commands. The panel shows each board's source and scope read-only, so a missing ticket can be explained. The presets edit the query text.

**Detail pane.** Opens at once from the stored row. Sections, toggled by the digits 1 to 6: facts, description, score and eligibility (the content of `why`), links and blockers, comments (the only section read lazily, with `ticketctl get --comments 10`, cached for 50 entries by `(site, key, updated)`, at most 8 KiB per comment and 64 KiB per pane, with "(N more characters)"), and claim and manual-order history. Text is sanitized and never parsed as markup; highlighting is bounded; link targets are shown.

**Refresh.** `r` re-reads the highlighted ticket live with `ticketctl get` (through the store writer) and never opens the pane. `R` runs the incremental `refresh`. An automatic refresh runs every `browse.refresh_interval` and reads the store first. Every refresh takes the same lease as cron; a second caller just reads the store. Selection and scroll survive a refresh; a failed board marks its rows stale and keeps the data; a refresh clears the comments cache and closes the detail pane of a ticket that became hidden. Reads cancel between calls, tracked child process groups are killed on quit and the timer stops on every exit path.

**Actions** (each is also a CLI command; the TUI calls the same functions in process, with actor `human:<me.name>` and `actor_source: tui`). The TUI's holder is `browse:<me.name>`, so two people's TUIs differ. The bindings, from which `?` generates its help table, are:

| Key | Context | Action |
|---|---|---|
| `up`, `down`, `enter` | list | move; `enter` opens the detail pane |
| `tab` | list | switch board |
| `left`, `right`, `h`, `l` | list | scroll by column |
| `H` | list | header cursor; sorts on enter or space |
| `1` to `6` | pane | toggle a detail section |
| `p` | list | pin or unpin |
| `K`, `J` | list | move up or down in the pin list; an unpinned ticket is first pinned at the end (as `pin`) |
| `x` | list | skip (untimed), or unskip a skipped ticket |
| `c` | list | claim with holder `browse:<me.name>` |
| `u` | list | release the TUI's own claim |
| `U` | list | force-release any claim after a confirmation dialog showing the holder and the claim's labels; the dialog stands in for the `--force` TTY test, and the in-process force argument is reachable from no flag, environment variable or config key |
| `r` | list | re-read the highlighted ticket |
| `R` | list | incremental refresh |
| `ctrl+r` | list | re-rank (the TUI owns the keyboard, so this is not a shell binding) |
| `o` | list | open the ticket's browse URL; the TUI stays open |
| `a` | list | toggle ineligible tickets with their reasons |
| `/` | list | filter |
| `F` | list | query panel |
| `m`, `d`, `b`, `c` | query panel only | presets mine, due soon, blocked, claimed |
| `D` | query panel | write the default query |
| `S` | list | select the highlighted ticket to start (see the result file) |
| `?` | any | help |
| `q` | any | quit |

The opener accepts only a URL matched with `fullmatch` against `^https://[A-Za-z0-9.-]+(:[0-9]{1,5})?/[A-Za-z0-9._~/?=&#%:@+,;-]*$` that ends in the row's key (ticketctl's built `https` URL, no userinfo). It runs it as one argv element through `wslview` (WSL), `xdg-open` (Linux) or `open` (macOS), never `cmd.exe`, with the environment `PATH`, `HOME`, `DISPLAY`, `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_CURRENT_DESKTOP` and `BROWSER`, detached, with the standard streams on `/dev/null`. `S` exits at once with intent `start` and exactly one `selected`; on a ticket failing a hard rule (other than `claimed` by this TUI's own claim) it shows an error instead. When the ticket carries a claim made by this TUI (holder `browse:<me.name>`), `S` releases that claim when it writes the start result, so the starting tool can claim with its own holder; a cron `next --claim` could take it in that moment, in which case the starter reports `claimed`.

**Result file.** With `--result-file`, on exit 0 the TUI writes `{"intent": "start"|"open"|"back", "selected": [{"key", "site", "board"}]}` (schema `schemas/cli/browse-result.json`); `start` means the user pressed `S` on a ticket and wants it started, `open` that the user opened the browse URL (with the last opened ticket) and `back` that the user quit without either; on quit the intent is `open` if a URL was opened, else `back`. It carries ids only and no ticket text. At start an existing path is accepted only when it is a regular file owned by the user that is empty or a valid `browse-result.json` document of at most 4 KiB (it is then removed); anything else exits 2 `invalid_argument`, reason `result_file_exists`. `open` asks the caller for nothing (the URL is already open). The file is written as a temp file (exclusive, no links, mode 0600) and renamed; a symlink or non-regular target is refused; a signal exit leaves no file. Without the flag nothing is written.

The TUI runs correctly as a foreground child of another TUI, respects the terminal's colors and never hard-codes a background. Resizing is supported down to 10 columns.

## Upgrades

The state database is versioned; migrations are additive only, so a newer tool can read an older store, and an older tool reading a newer store exits 12 (`schema_newer`). `--json` outputs and hook payloads gain fields additively. Unimplemented commands in a release exit 12 `not_implemented`.

## Residual risks

- A prompt-injected ticket can steer the order of the tickets inside the re-rank's candidate set. The effects are bounded by validation (exact key set), by the slot rule (a re-rank only reorders the slots its covered tickets already hold), by pins and hard rules, and by the fact that a ticket is only handed out for a human or a caller to act on. No re-rank output is acted on as an instruction.
- The sandbox's containment was not attacked in the design-time spike (the injected instructions were not obeyed, so the sandbox was never exercised); a live containment test is a still-to-verify item. What `preferred` and `required` do when `bwrap` or `socat` is missing is in the Sandbox paragraph of [Slot contract](#slot-contract).
- Ticket text is stored on disk (the store, the run directory while a re-rank runs). claude-session keeps a re-rank's session directory and input until its `retention_days` after `forget`, and Claude Code keeps a transcript with the fenced input under `~/.claude/projects` indefinitely; ticket-queue sweeps its own run directories and sessions (see [Slot contract](#slot-contract)), but Claude Code transcripts remain.
- A claim is local to one machine's store. Two machines (or two state directories) can hand out the same ticket; the caller's own write to the ticket system (an assignment) is what coordinates them.
- A report command containing `$CSESSION_DIR` is denied by claude-session and the model may then give up; the trusted prompt uses absolute paths, which reduces but does not remove the chance. A run that never reports ends `unreported` and falls back to the deterministic order.
- `blocked` and `estimate` are only as good as ticketctl's reading of links and the points fields; an ambiguous points field excludes every ticket on a board until it is mapped (`estimate_ambiguous` names the key to set).
- The cron-filled store can be up to `refresh.stale_after` old when read; `claim` re-reads the ticket live, but `list` and `next` without `--claim` show stored data. A ticket outside the re-read set (claimed, pinned, the top 100 candidates) can be stale until it changes or the next full rebuild, and pool membership changes are seen only by a complete full rebuild (`refresh.full_every`, default 24 hours; lower it to shorten this).
- A custom `rerank.command` is not stopped by a SIGKILL of ticket-queue.
- With `rerank.sandbox: preferred` and no active sandbox, a prompt-injected session could try to make `claude-session report` read a file (`--summary-file`, `--reason-file`) and move its content into the report. The bundled profile denies those forms and the trusted prompt uses an inline summary, but the deny rules' wildcard syntax is not live-verified.
- A ticket moved into a hidden project whose new key a search returned before any `get` recorded the alias stays a separate visible row until `prune`.
- A local clock ahead of the ticket system by more than `refresh.overlap` can make the watermark miss updates until the next full rebuild; tune `refresh.overlap`.
- Editing a hook's `cmd` abandons its pending events (they end with a final `hook_failed` after their retries); `validate` reports them as `orphan_events`.
- A noisy writer can rotate old records out of `log.jsonl` (`log.max_bytes` × `log.keep`); hooks such as `post-release` are the durable channel.
- A caller allowed `claim` can claim every ticket for `claim.max_ttl` and keep renewing; `claims` shows it.
- Ticket authors set priority, due date, sprint and labels, so a ticket can rank itself first without any model; handing a ticket out is not an endorsement of its text.
- The re-rank session holds the model credential (`claude_session.pass_env`); a hostile ticket can write what the session can read into `reason` (200 characters each), which `why` and the TUI print.

## Platform notes

Linux and WSL (Ubuntu) are required. macOS is supported on a best-effort basis: there is no Linux-only code, the re-rank sandbox uses Seatbelt where claude-session supports it, and a macOS checklist is part of the live suite. File locking and the lease use portable primitives. Under WSL, `bubblewrap` and `socat` are needed for a sandboxed re-rank; WSL1 has neither; see the Sandbox paragraph of [Slot contract](#slot-contract) for what `preferred` and `required` then do.
